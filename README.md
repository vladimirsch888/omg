# Учёт выручки — SaaS для доходов/расходов, PnL, ДДС и LTV

Веб-приложение для учёта доходных и расходных операций по лицензиям
(amoCRM, Wazzup, NOVA) и по работам/сопровождению собственных клиентов.
Показывает прибыль компании, PnL (по методу начисления), ДДС (кассовый
метод) и LTV клиента, с учётом иерархии проектов и трудозатрат по заявкам.
Полностью адаптировано под мобильные экраны (проверено на эмуляции
iPhone в Safari/Chrome).

## Стек

```
apps/api   — Node.js 24 LTS + Hono + TypeScript + Prisma 7 (Rust-free, pg driver adapter) + PostgreSQL 16
apps/web   — React 19 + Vite 8 (Rolldown) + TypeScript + Tailwind CSS v4 + Recharts 3
```

### Почему именно так (важно для VPS с ограниченной памятью)

Задача была не просто "написать сервер", а сделать его лёгким и быстрым
на недорогом VPS. Поэтому вместо привычной связки Express + Prisma
(с Rust-движком) выбрано следующее:

- **Hono** вместо Express — по независимым бенчмаркам 2026 года
  обрабатывает в разы больше запросов в секунду и потребляет заметно
  меньше памяти на соединение, при этом это mainstream-фреймворк,
  а не экзотика: работает на обычном Node.js через `@hono/node-server`.
- **Prisma 7 в Rust-free режиме** — начиная с Prisma 7 клиент больше не
  тянет отдельный Rust-бинарник query-engine (раньше это была
  дополнительный процесс на десятки мегабайт памяти и медленный старт).
  Запросы идут напрямую через драйвер `pg` (`@prisma/adapter-pg`).
  В этом проекте собранный API стартует и стабильно держит **~85–110 МБ
  RSS** памяти на реальном Postgres 16 (замерено на Ubuntu 24.04).
- **Node.js 24 LTS** — актуальный LTS-релиз на 2026 год, ставится на
  Ubuntu 24.04 одной командой через официальный репозиторий NodeSource
  (в стандартных репозиториях Ubuntu 24.04 версия Node.js устаревшая).
- **TypeScript 7** (нативный компилятор на Go, «tsgo») — тот же пакет
  `typescript` и та же команда `tsc`, но проверка типов и сборка в
  8–12 раз быстрее предыдущей версии на JS/Rust.
- **Vite 8 на движке Rolldown** (Rust-бандлер) — сборка фронтенда занимает
  ~1 секунду даже на скромном CPU, что удобно при деплое прямо на VPS.
- **Tailwind CSS v4** — новый Rust-движок (Oxide), меньше итоговый CSS,
  конфиг прямо в CSS-файле без `tailwind.config.js`.
- **React 19 + React Router 7** — актуальные стабильные версии,
  фронтенд собирается в статические файлы и раздаётся Nginx — сам React
  не потребляет ресурсы сервера, только браузер клиента.

Итог: PostgreSQL + один Node-процесс с Hono/Prisma спокойно работают на
VPS с 1 vCPU / 1 ГБ RAM, что обычно узкое место для связки
Express+Prisma+Rust-engine.

### Модель данных (apps/api/prisma/schema.prisma)

- **Organization** — компания (мультитенантность заложена на будущее).
- **User** — вход по email/паролю, роли `OWNER / ADMIN / MANAGER / VIEWER`
  и `tokenVersion`: при смене пароля, роли, отключении пользователя или
  «Выйти на всех устройствах» он увеличивается, и все ранее выданные токены
  перестают приниматься (см. «Безопасность» ниже).
- **Client** — клиент B2B (юрлицо, ИНН, контакты, статус).
- **Project** — трёхуровневая структура **клиент → проект → подпроект**:
  у проекта есть `clientId` и необязательный `parentId`. Подпроект — это
  тот же `Project` с заполненным `parentId`; глубина ограничена одним
  уровнем вложенности (у подпроекта не может быть своих подпроектов).
  Деньги и часы подпроекта **не дублируются**, а агрегируются в отчётах
  родителя через рекурсивный обход дерева (`getProjectAndDescendantIds`).
  Статус `CLOSED` означает "работы по проекту завершены": кнопка «Проект
  завершён» ставит его вместе с сегодняшней датой в `endDate`, и проект
  становится серым в списках. Возврат в работу очищает `endDate`, чтобы
  случайное нажатие не оставило после себя выдуманную дату окончания.
- **AuditLog** — журнал изменений: кто, когда и что создал/изменил/удалил
  (плюс продления и входы). `entityId` — обычная строка, а не связь, поэтому
  записи переживают удаление самого объекта. Раздел «Журнал» в админке.
- **DictionaryType / DictionaryValue** — универсальный справочник
  ("разделы" и их значения), который можно наполнять из админки:
  из коробки заведены разделы `operation_category` (категории операций,
  включая лицензии amoCRM/Wazzup/NOVA, работы, сопровождение, зарплата,
  закупка лицензий и т.д.), `project_type`, `payment_method`, `account`
  (счета и кассы — через них считается остаток по каждому счёту),
  `request_type` — плюс можно создавать свои разделы.
- **Operation** — доходная/расходная операция: сумма, привязка к проекту,
  счёт/касса (`accountValueId`), признак `taxPayment` (расход — уплата
  налога, уменьшает ещё не уплаченный резерв),
  категория из справочника, `accrualDate` (дата начисления — для PnL) и
  `paymentDate` (дата фактической оплаты — для ДДС), плюс `vendorSharePercent`
  и `taxable` для финансового водопада (см. ниже).
- **LicenseProduct** — товарная матрица (раздел **Продукты**): название,
  категория, цена/доля вендора/налогообложение по умолчанию, и `type`:
  - `LICENSE` — лицензия по подписке: есть `defaultDurationMonths` (срок,
    на который продлевается подписка).
  - `WORK` — разовая работа: `defaultDurationMonths` всегда `null` (у
    работы нет цикла продления), вместо этого при продаже указывается
    `workEndDate` (см. Sale ниже). Есть свой аналог срока —
    `defaultWorkDays` (оценка в рабочих днях, необязательна), которым
    предзаполняется поле «Срок выполнения» на форме продажи и по которому
    считается дата окончания работ (apps/web/src/utils/format.ts,
    `addWorkingDays` — прибавляет N рабочих дней, пропуская
    сб/вс, без учёта праздников). Такой продукт нельзя выбрать при
    создании Subscription — только через Продажи.
- **Subscription** — проданная клиенту лицензия (только `type: LICENSE`):
  свой снимок цены/срока/доли вендора/налогообложения (независимо от того,
  что потом изменится в каталоге), `nextBillingDate` — когда выставлять
  следующий платёж.
- **Sale** — разовая продажа продукта клиенту (раздел **Продажи**, любой
  `type`): в отличие от Subscription не имеет цикла выставления счетов —
  операции создаются один раз, датой продажи. `clientId` обязателен,
  `projectId` опционален — как и у Subscription (см. "Целостность связей"
  ниже). `workEndDate` ("Дата окончания работ") заполняется только для
  продажи `WORK`-продукта — вместо срока подписки у разовой работы есть
  дедлайн.
- **Request** — заявка клиента, привязана к проекту.
- **TimeEntry** — часы сотрудника по проекту и, опционально, по заявке.

### Финансовый водопад: продажа лицензий и услуг (apps/api/src/modules/finance)

Бизнес-модель: два источника дохода — **услуги** (внедрение, ежемесячное
сопровождение — доля вендора 0%) и **лицензии** (доля вендора обычно 50%,
т.к. по ним есть партнёрский договор с поставщиком). У каждой INCOME-операции
есть `vendorSharePercent` и `taxable`, и `computeWaterfall()`
(`apps/api/src/modules/finance/waterfall.ts`) считает:

```
сумма от клиента
  → минус доля вендора (vendorSharePercent %)     = что осталось после вендора
  → минус резерв на налог (taxReservePercent %,    = свободно к использованию
      пропускается если taxable=false — оплата
      «на карту» без учёта налога)
```

`taxReservePercent` (сейчас 7% — упрощённая модель УСН "доходы", без учёта
поквартальных порогов) задаётся в `config.taxReservePercent`
(`TAX_RESERVE_PERCENT` в `.env`). Доля вендора списывается не абстрактно, а
реальной EXPENSE-операцией (категория `license_cost`) — она видна в
Операциях и PnL как обычный расход. Резерв на налог — не отдельная
операция, а расчётная метрика (`/api/reports/cash-position`): "сколько денег
физически на счетах" минус "сколько накопительно отложено с облагаемых
доходов" = "сколько реально свободно". Точный учёт уплаты налога поквартально
— осознанно не сделан, будет отдельной доработкой.

**Продажа лицензии с продлением = Subscription.** Создание подписки (`POST
/api/subscriptions`) сразу выставляет первый платёж: создаёт INCOME-операцию
и, если есть доля вендора, связанную EXPENSE-операцию. Дальше на каждый новый
период — одна кнопка «Продлить» (`POST /api/subscriptions/:id/bill`), которая
проделывает то же самое. Именно это описывалось как "продублировать заказ на
следующий месяц одной кнопкой". Перед продлением фронтенд запрашивает
подтверждение суммы (по умолчанию — текущая цена подписки); если ввести
другую сумму, `POST .../bill` принимает необязательный `amount` — платёж за
этот период пройдёт по новой сумме, и она же сохранится как `price`
подписки, то есть станет суммой по умолчанию и для всех следующих продлений.

**Стадия «Счёт отправлен».** Перед продлением есть промежуточный шаг:
`Subscription.invoiceSentAt` — дата, когда клиенту выставили счёт за
следующий период. Деньги ещё не пришли и ничего не проведено, поэтому это
не операция, а пометка: строка подписки подсвечивается жёлтым из палитры
(`reserve-soft` — тёплая охра в тёмной теме, светло-жёлтый в светлой) и
получает бейдж «счёт от <дата>». `POST /api/subscriptions/:id/invoice-sent`
ставит отметку, `DELETE` того же адреса снимает её (на случай ошибочного
нажатия), а `billSubscription` очищает её сам: продление закрывает тот
период, ради которого счёт и выставляли, и новый цикл начинается без
выставленного счёта. Дата, а не флаг — чтобы в списке было видно, сколько
клиент уже сидит на счёте.

Дата операции и дата следующего платежа считаются раздельно, и это важно для
просроченных подписок: сама операция (INCOME/EXPENSE) датируется моментом
нажатия «Продлить» (`new Date()`) — когда деньги реально пришли, а не когда
подписку формально надо было продлить, — а вот `nextBillingDate` продвигается
на `durationMonths` (1, 6, 7, 12, 13, 25 — любой срок, не привязан к
календарным месяцам) от *прежнего* `nextBillingDate`, а не от даты клика. Это
намеренно: если продлить просроченную подписку сегодня, платёж должен
попасть в сегодняшний месяц как факт, а график следующих платежей не должен
"поехать" из-за того, что оплатили с опозданием. Раньше операция датировалась
старым (просроченным) `nextBillingDate` — из-за этого платёж по просроченной
подписке "терялся" в прошлом месяце, а сама подписка продолжала висеть в
разделе "ожидается" как будто её не продлевали (issue исправлен).

Раздел **Подписки** также показывает сводку за текущий календарный месяц
(`GET /api/subscriptions/month-summary`, `getMonthSummary` в
subscriptions.service.ts):

- **Общая сумма подписок в этом месяце** — уже продлено плюс ещё ожидается
  до конца месяца.
- **Уже продлено в этом месяце** — сумма INCOME-операций от подписок с
  `accrualDate` в текущем месяце.
- **Ожидаем поступление** — сумма цен активных подписок, по которым нажата
  «Счёт отправлен» (`invoicedAmount`, плюс счётчик `invoicedCount`). Это
  **подмножество** ожидаемой суммы, а не добавка к ней: та же подписка
  продолжает учитываться в прогнозе, пока «Продлить» не проведёт платёж.
  Намеренно не ограничено текущим месяцем — счёт, выставленный в августе и
  до сих пор не оплаченный, это деньги, которых ждут сегодня.
- **Чистая прибыль с продлённых** — те же операции, но не просто доход
  минус EXPENSE: это `spendable` из `computeWaterfall` (доход минус доля
  вендора **и** налоговый резерв — обе ставки сразу, а не только вендор),
  уже по факту.
- **Ожидаемая прибыль до конца месяца** — чистый прогноз, **без факта**:
  только по подпискам, которые ещё предстоит продлить в этом месяце
  (`status: ACTIVE`, `nextBillingDate` до конца месяца включительно —
  попадают и просроченные продления), тот же `spendable` через
  `computeWaterfall` по условиям каждой подписки. Уже продлённые в этом
  месяце сюда не входят — они в «Чистой прибыли с продлённых». Поэтому
  годовая лицензия, оплаченная в начале месяца и уходящая на следующий год,
  здесь не показывается: для этого месяца она закрыта. Обычно продление
  сразу выводит подписку из "ожидается" (её новый `nextBillingDate` уходит за
  пределы месяца), и деньги "переезжают" из этого прогноза в факт. Но если
  подписка была просрочена настолько, что даже следующий период по графику
  всё равно попадает в этот же месяц — она законно останется в "ожидается"
  и после продления: это не задвоение, а два разных периода оплаты,
  выпавшие на один календарный месяц.

**План продаж = SalesPlan** (`apps/api/src/modules/salesPlans`). Модель хранит
одну цель: `year` + `month` (1..12 — план на месяц, `null` — годовой план) +
`amount`. Годовой и месячные планы задаются независимо и не обязаны сходиться
— когда они расходятся, интерфейс показывает и сумму месячных планов рядом с
годовым. Уникальность (organizationId, year, month) проверяется в сервисе, а
не уникальным индексом: Postgres считает NULL-ы различными, поэтому индекс
разрешил бы два годовых плана на один год.

- `GET /api/sales-plans?year=` — сами планы, `PUT /api/sales-plans` — сохранение
  годового и всех двенадцати месячных за один запрос (страница редактирует их
  на одном экране, пустое значение = план снят).
- `GET /api/sales-plans/report?year=` — план против факта по месяцам плюс
  структура прибыли. **Факт** — начисленная выручка (та же база, что в PnL):
  цель по продажам меряется выручкой месяца, к которому доход относится, а не
  датой, когда деньги дошли.

**Прогноз по активным подпискам.** Отчёт дополнительно проходит по графику
каждой активной подписки до конца года и раскладывает ещё не выставленные
периоды по месяцам (`months[].subscriptionForecast`, итог —
`totals.forecast` = факт + прогноз). Это предсказуемая часть будущей
выручки: подписка с известной ценой и циклом выставится независимо от того,
продадут ли что-то новое. Два правила: прогноз ставится только на текущий
месяц и дальше (иначе прошлые месяцы врали бы о том, что уже случилось), а
просроченная подписка проецируется в текущий месяц — эти деньги ожидаются
сейчас, ровно как в разделе Подписки. На графике прогноз идёт полупрозрачным
сегментом поверх фактического столбца, а карточка «Выполнение плана»
показывает **две шкалы**: по годовому плану и по плану текущего месяца, в
каждой — факт сплошной заливкой плюс прогноз по подпискам.

Разбивка **чистой прибыли на лицензии и работы** (та, что показывается рядом с
графиком) идёт по наиболее надёжному доступному признаку, в порядке убывания
достоверности: операция от подписки — всегда лицензия; операция от продажи —
по типу продукта (WORK/LICENSE); ручная операция — по её категории, если
каталог продуктов однозначно связывает эту категорию с одним типом; наконец,
ручная операция с долей вендора — лицензия (в этом бизнесе долю платят только
за перепродажу лицензии). Остальное честно попадает в «Прочее», а не
распихивается по двум корзинам ради красивых процентов. Связь «категория →
тип» выводится из каталога организации, а не зашита кодами справочника: коды
пользователь может переименовать, а добавив свой продукт нужного типа с этой
категорией, он сразу получает правильную разбивку.

**Разовая продажа = Sale** (`POST /api/sales`, apps/api/src/modules/sales).
Тот же принцип waterfall и тот же паттерн (INCOME + связанная EXPENSE на
долю вендора), но без цикла продлений — используется, когда продление
вести не нужно (или ведётся отдельными продажами). Форма — ровно четыре
поля: клиент, проект (опционально), продукт, сумма; доля вендора и
налогообложение берутся из умолчаний продукта.

#### Целостность связей клиент/проект/продукт/продажа

И Subscription, и Sale всегда несут `clientId` напрямую, даже когда
`projectId` не указан — иначе часть выручки клиента была бы невозможно
отнести ни к одному клиенту через проект. Из этого следуют два места,
которые обязаны учитывать все три пути привязки (проект → клиент,
подписка → клиент, продажа → клиент), а не только через проект:

- **`getClientLTV`** (`apps/api/src/modules/reports/reports.service.ts`) —
  запрашивает операции по `OR`-условию `project.clientId` /
  `subscription.clientId` / `sale.clientId`, а не только через
  `client.projects.flatMap(...)`, иначе продажи/подписки без проекта были
  бы не видны в LTV клиента.
- **PnL/ДДС с фильтром по клиенту** (`resolveScopeWhere`) — тот же принцип:
  фильтр по `clientId` собирает операции через все три связи, а не только
  через проекты клиента.

При создании Subscription/Sale с указанным `projectId` бэкенд проверяет,
что `project.clientId` совпадает с переданным `clientId` (по аналогии с
проверкой родитель/подпроект при создании Project) — иначе выручка клиента
могла бы "утечь" на чужой проект и разъехаться в отчётах по проектам и по
клиентам.

### Отчёты (apps/api/src/modules/reports)

- **PnL** (`/api/reports/pnl`) — выручка/расходы по методу начисления
  (`accrualDate`), помесячно и по категориям, с фильтром по проекту
  (с роллапом подпроектов) или клиенту.
- **ДДС** (`/api/reports/dds`) — движение денег по кассовому методу
  (`paymentDate`), приток/отток/накопленный остаток.
- **LTV клиента** (`/api/reports/ltv`) — суммарная выручка, расходы и
  чистая прибыль по клиенту за всё время, средняя выручка в месяц.
- **Сводка компании** (`/api/reports/summary`) — данные для дашборда:
  текущий месяц, тренд за 12 месяцев, топ клиентов по LTV, часы за месяц.
- **Сводка по проекту** (`/api/projects/:id/summary`) — доход/расход/
  прибыль/часы по проекту **с учётом всех его подпроектов**, плюс
  `timeline` — фактический срок реализации (см. ниже).
- **Деньги на руках** (`/api/reports/cash-position`) — сколько денег
  физически на счетах (в целом и по каждому счёту/кассе), сколько
  **ещё не уплаченного** резерва на налог (начислено с облагаемых доходов
  минус расходы с признаком «уплата налога») и сколько свободно. Без
  вычета уплаченного налога резерв рос бы вечно, а уплаченный налог
  наказывал бы свободные деньги дважды.
- **ДДС с `from`** возвращает `openingBalance` — деньги, накопленные до
  начала периода; накопленный остаток стартует с него, поэтому «Остаток на
  конец периода» за 12 месяцев совпадает с «Всего на счетах» на дашборде.
- **Напоминания** (`/api/reminders`) — просроченные и ближайшие (7 дней)
  продления, счета старше 14 дней без оплаты, сроки работ, срочные заявки.
  Показываются на дашборде в блоке «Требует внимания»; при заданных
  `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` тот же список раз в день уходит
  в Telegram (`TELEGRAM_DIGEST_HOUR`, по умолчанию 9:00 по TZ сервера).
- **Экспорт CSV** (`/api/export/{operations,sales,subscriptions,time-entries,pnl,dds}.csv`)
  — те же фильтры, что у списков; UTF-8 с BOM, разделитель `;`, десятичная
  запятая — открывается в Excel без мастера импорта.

#### Завершение проекта и фактический срок реализации

Кнопка «Проект завершён» (на карточке проекта и в списке) переводит его в
статус `CLOSED` и записывает сегодняшнюю дату в `endDate`; «Вернуть в работу»
возвращает `ACTIVE` и очищает `endDate`. Завершённый проект показывается
серым — приглушённые название и карточка (`opacity-70`), а завершённые
подпроекты ещё и зачёркнуты, — так что список читается как "что в работе, а
что уже сделано", без отдельного фильтра.

Внутри проекта блок **«Срок реализации»** отвечает на вопрос "сколько по
факту заняли работы" (`buildProjectTimeline` в projects.service.ts, данные
приходят в `timeline` из `GET /api/projects/:id/summary`):

- **Начало работ** — `startDate` проекта, если его заполнили; иначе самое
  раннее реальное событие по проекту: операция, заявка или списанные часы.
  В подсказке под датой прямо написано, откуда она взята (`startSource`),
  чтобы цифру можно было проверить, а не принимать на веру.
- **Завершение** — `endDate` проекта, который ставит кнопка «Проект
  завершён» (или заполненная вручную дата окончания работ); если проект
  закрыли без даты, берётся последняя активность. Пока проект в работе, поле
  показывает "в работе", а срок считается по сегодняшний день — то есть
  число всё время означает "сколько это уже длится".
- **Фактический срок** — в календарных днях (включая обе граничные даты) и
  отдельно в рабочих днях (без суббот и воскресений, производственный
  календарь не учитывается). Рабочие дни — та же единица, в которой
  оценивается WORK-продукт (`defaultWorkDays`), поэтому план и факт можно
  сравнить напрямую.

Даты берутся по проекту **и всем его подпроектам** — реальный срок родителя
обязан покрывать работы, которые велись внутри него (это тот же
`getProjectAndDescendantIds`, что и для денег с часами).

### Безопасность и права

- **Проверка пользователя на каждом запросе.** `requireAuth` не доверяет
  роли из токена: по `userId` читается актуальная запись, и отключённый
  пользователь, изменённая роль или увеличенный `tokenVersion` дают 401
  сразу, а не через 7 дней жизни токена.
- **Роли.** `VIEWER` — только чтение: любой POST/PATCH/PUT/DELETE под
  `/api` отклоняется одним middleware (`blockViewerWrites`), интерфейс для
  него прячет кнопки. `ADMIN` не может назначать роль `OWNER`, трогать
  владельцев, менять собственную роль или отключать себя; последний активный
  владелец не может быть понижен или отключён.
- **Регистрация закрыта** по умолчанию: `POST /auth/register` работает,
  пока в базе нет ни одной организации (первый запуск), либо при
  `ALLOW_REGISTRATION=true`. Экран входа спрашивает
  `GET /auth/registration-status` и не показывает ссылку «Создать компанию»,
  если регистрация закрыта.
- **Пароли** — минимум 8 символов, не из одного повторяющегося символа и не
  только цифры (`passwordSchema`); вход и регистрация ограничены по
  частоте (10 и 5 попыток в минуту с одного IP, `rateLimit`).
- **Смена пароля** (`POST /auth/change-password`) и **выход везде**
  (`POST /auth/logout-all`) — в «Настройки → Безопасность».
- **Ссылки на чужие записи** (проект, клиент, продукт, значения
  справочников) проверяются на принадлежность организации и в POST, и в
  PATCH (`utils/ownership.ts`); дерево проектов защищено от циклов,
  превышения глубины и переноса подпроекта на другого клиента.
- **Ошибки** — некорректный JSON, невалидная дата или enum, дубликат кода,
  ссылка на несуществующую запись отвечают 400/404/409 с понятным
  сообщением, а не 500 (`app.onError`).
- **Заголовки** `X-Frame-Options`, `X-Content-Type-Options`,
  `Referrer-Policy`, `Cache-Control: no-store` ставит API; Nginx добавляет
  свои и HSTS при HTTPS. `JWT_SECRET` обязателен, короче 32 символов или
  равный плейсхолдеру — сервер не стартует.

### Frontend (apps/web/src)

Разделы: Дашборд (включая карточки "Деньги на руках"), Клиенты, Проекты
(дерево клиент→проект→подпроект, кнопка «Проект завершён» и отчёт по сроку
реализации внутри проекта), Операции, **Продукты** (товарная матрица:
лицензии по подписке и разовые работы — тип продукта переключается в
форме), **Продажи** (разовая продажа: клиент, проект опционально, продукт,
сумма, плюс "Дата окончания работ" когда продукт типа "Работа"),
**Подписки** (продажа лицензий с продлением, кнопка «Продлить», история
платежей, поиск и фильтр по статусу — доступны только продукты-лицензии),
**План продаж** (годовой и месячные планы, график план/факт и доля чистой
прибыли по лицензиям и работам рядом с ним), Заявки, Учёт часов (с
пагинацией и фильтрами), отчёты PnL и ДДС (выбор периода, разрез по клиенту
или проекту, экспорт), а также админка: Справочники, Пользователи
(редактирование, смена пароля, отключение), Журнал изменений и Настройки
(тема, свой пароль, выход везде, Telegram, демо-данные). Списки операций,
клиентов, продаж, заявок и проектов ищутся и фильтруются; операции
листаются страницами, поддерживают дублирование и массовое удаление;
продажу можно «продать ещё раз». Карточка клиента показывает его
подписки, проекты и продажи; карточка проекта — план/факт по часам и
стоимость часов по ставке. Дашборд показывает остатки по счетам и блок
«Требует внимания». Даты по умолчанию в формах берутся в местном времени
(`todayInput()`), а не в UTC. Несуществующий адрес показывает страницу
«Такой страницы нет»; потеря связи с сервером — общий тост.

#### Дизайн-система

Две темы на одном наборе имён. Палитра задаётся через `@theme` в
`src/index.css` — поверхности (`canvas` → `surface` → `raised` → `overlay`),
линии, текст (`ink` / `ink-muted` / `ink-subtle`), акцент (приглушённый
петроль) и три финансовых цвета: `income` (сдержанный изумруд), `expense`
(терракота), `reserve` (охра). Тёмная тема (тёплый графит, не чёрный) —
значение по умолчанию; светлая (тёплый белый) переопределяет те же
переменные в блоке `:root[data-theme="light"]`, поэтому ни один `bg-surface`
или `text-ink` в коде не знает о существовании тем. Ярких «светофорных»
красного и зелёного нет намеренно — именно они делают финансовый интерфейс
дешёвым и тревожным. Шрифт — Inter (self-hosted, без внешнего CDN), все
денежные суммы идут табличными цифрами (`.tnum`), чтобы колонки не «прыгали».

Тему выбирает пользователь в **Настройки → Оформление**: «Как в системе»
(по умолчанию, следует `prefers-color-scheme`), «Светлая» или «Тёмная».
Выбор хранится в `localStorage` и применяется `ThemeContext`
(`src/context/ThemeContext.tsx`), а инлайновый скрипт в `index.html`
проставляет `data-theme` **до первой отрисовки** — иначе страница успевает
мигнуть тёмной темой перед монтированием React. Раздел «Настройки» открыт
всем ролям, потому что тема — личная настройка; блок управления
демо-данными внутри страницы по-прежнему виден только владельцу и
администратору.

Общие компоненты — `src/components/ui`: `Button`/`IconButton`, `Field` +
`Input`/`Select`/`Checkbox`, `Badge`/`StatusBadge`, `Card`/`ListCard`/
`StatCard`/`PageHeader`, `DataTable`, `Modal`, `Skeleton`/`EmptyState`,
`Sparkline`. Два принципиальных момента:

- **`DataTable` рендерит одни и те же данные двумя способами**: таблицей от
  `sm` и вверх, а на телефоне — карточками (`RowCard`). Горизонтального
  скролла таблиц в приложении нет вообще.
- **`UiProvider` заменяет `window.confirm` / `prompt` / `alert`** на
  собственные модалки и тосты: `const ui = useUi()` → `await ui.confirm(...)`,
  `await ui.prompt(...)`, `ui.toast(...)`. Системные диалоги браузера на iOS
  показывают домен сайта над текстом и не поддаются стилизации.

Навигация: на десктопе — сайдбар с иконками, сгруппированный по смыслу
(`src/components/nav.ts`); на телефоне — нижний таб-бар с пятью пунктами и
шторкой «Ещё», плюс липкая шапка с названием текущего раздела. Тап-таргеты
не меньше 44px, safe-area учтена сверху и снизу.

#### Графики (src/components/charts)

Recharts — самая тяжёлая зависимость фронтенда, поэтому каждый график
подключается через `React.lazy` и обёртку `LazyChart`: страница со списком
не тянет библиотеку вообще (основной бандл ~410 кБ вместо ~760 кБ). Общий
вид задан в `charts/theme.ts` — тонкие линии, только горизонтальная сетка,
свои тултипы (`ChartTooltip`) и сокращённые подписи осей (`450 тыс`,
`1,2 млн`, через неразрывный пробел, чтобы подпись не переносилась).
Recharts принимает цвета строками и не умеет читать CSS-переменные, поэтому
обе палитры лежат в том же файле, а хук `useChartColors()` отдаёт нужную —
он же перерисовывает графики при смене темы.
Спарклайны в KPI-карточках нарисованы вручную на SVG (`ui/Sparkline.tsx`) —
ради них не имеет смысла грузить recharts на первый экран.

### Демо-данные (apps/api/src/modules/demo)

У Client, Project, Operation, Request и TimeEntry есть флаг `isDemo`.
Раздел **Настройки → Демо-данные** в интерфейсе даёт две кнопки:

- **Наполнить демо-данными** (`POST /api/demo/seed`) — создаёт для текущей
  организации 4 демо-клиентов, 7 проектов (включая подпроекты, чтобы
  показать роллап, и один уже завершённый — с заполненными датами начала и
  окончания, чтобы сразу было видно серое отображение и отчёт по сроку
  реализации), 6 продуктов (4 лицензии + 2 разовые работы), 4 подписки
  с историей платежей, 4 разовые продажи (включая продажи без привязки к
  проекту — чтобы проверить, что LTV и отчёты по клиенту не теряют такую
  выручку — и продажу WORK-продукта с заполненной "Датой окончания работ"),
  операции за последние ~8 месяцев по всем категориям (лицензии
  amoCRM/Wazzup/NOVA, работы, сопровождение, зарплата, хостинг, маркетинг
  и т.д. — включая один запланированный, но неоплаченный доход, чтобы PnL
  и ДДС различались), несколько заявок и записей учёта часов, а также планы
  продаж на текущий год — годовой и двенадцать месячных, намеренно не ровно
  по одной двенадцатой, чтобы на графике план/факт были и перевыполненные, и
  проваленные месяцы.
- **Удалить демо-данные** (`POST /api/demo/clear`) — удаляет только записи
  с `isDemo = true`; реальные данные пользователя не затрагиваются.

`GET /api/demo/status` возвращает текущие количества по каждой модели —
на них ориентируется кнопка "Удалить" (задизейблена, если демо-данных нет).

Вся логика в одном месте — `apps/api/src/modules/demo/demo.service.ts`
(`seedDemoData` / `clearDemoData` / `getDemoStatus`). Локальный
`prisma/seed.ts` (для разработки) вызывает тот же `seedDemoData`, так что
определение демо-данных не дублируется и не может разъехаться.

**Политика поддержки**: при добавлении новой фичи (новая модель, новая
категория справочника, новое измерение в отчётах) — расширять
`demo.service.ts`, чтобы демо-набор данных её тоже покрывал. Цель — чтобы
после нажатия "Наполнить демо-данными" ни один текущий раздел или отчёт
не оставался пустым/нулевым.

### Мобильная адаптация

- Боковое меню на десктопе превращается в выезжающую панель с
  кнопкой-гамбургером на экранах уже `lg` (≤1024px), включая iPhone.
- Все поля ввода — минимум 16px шрифта, иначе Safari на iOS
  автоматически зумит страницу при фокусе на поле (частый баг).
- Используются `dvh`-единицы высоты вместо `vh`, чтобы верстка не
  прыгала при скрытии/появлении панели адресной строки Safari.
- Учтены безопасные отступы `env(safe-area-inset-*)` под чёлку/индикатор
  жеста iPhone.
- Таблицы прокручиваются по горизонтали внутри карточки, а второстепенные
  колонки (категория, контакт, приоритет и т.п.) скрываются на узких
  экранах, чтобы ключевые цифры были видны сразу без прокрутки.
- Проверено эмуляцией iPhone 15 (Safari- и Chrome-варианты User-Agent)
  через headless Chromium — без горизонтального скролла страницы, меню
  и формы работают корректно.

## Запуск локально

1. Поднять PostgreSQL:
   ```bash
   docker compose up -d
   ```
2. Настроить переменные окружения API:
   ```bash
   cp apps/api/.env.example apps/api/.env
   # и обязательно задать JWT_SECRET (минимум 32 символа):
   #   openssl rand -base64 48
   ```
   Переменные: `DATABASE_URL`, `JWT_SECRET` (обязательные), `PORT`,
   `CORS_ORIGIN`, `TZ` (границы «сегодня» и «этот месяц» считаются в нём),
   `TAX_RESERVE_PERCENT`, `ALLOW_REGISTRATION`, `TELEGRAM_BOT_TOKEN`,
   `TELEGRAM_CHAT_ID`, `TELEGRAM_DIGEST_HOUR`.
3. Установить зависимости (из корня, монорепозиторий на npm workspaces):
   ```bash
   npm install
   ```
4. Применить миграции и (опционально) засеять демо-данные:
   ```bash
   npm run prisma:migrate --workspace apps/api
   npm run prisma:seed --workspace apps/api
   ```
5. Запустить API и веб отдельно:
   ```bash
   npm run dev:api   # http://localhost:4000
   npm run dev:web   # http://localhost:5173
   ```

Проверки качества (из корня): `npm run typecheck`, `npm run lint`
(ESLint для обоих приложений), `npm test` (vitest: водопад, даты
продлений, сроки проектов, политика паролей, CSV).

Демо-логин после `prisma:seed`: `owner@example.com` / `password123`.
Либо зарегистрируйте свою компанию прямо на экране входа — при
регистрации автоматически создаются справочники по умолчанию.

## Деплой: staging + production на одном VPS (Ubuntu 24.04)

Обе среды живут на одном сервере, каждая — со своей БД, своим `.env`,
своим systemd-сервисом и своим портом:

| Среда      | Ветка     | Директория                    | API порт | Сайт                     |
|------------|-----------|--------------------------------|----------|---------------------------|
| staging    | `staging` | `/opt/revenue-saas-staging`    | 4001     | `http://IP:8080/`         |
| production | `main`    | `/opt/revenue-saas-prod`       | 4000     | `http://IP/`              |

Деплой полностью автоматический через GitHub Actions
(`.github/workflows/deploy-staging.yml`,
`.github/workflows/deploy-production.yml`): пуш в `staging` разворачивает
staging, пуш в `main` — production. Ручных команд на сервере после
первичной настройки быть не должно.

### Единоразовая настройка сервера

1. Направить домен на IP сервера и запустить `deploy/bootstrap-vps.sh` на
   свежем VPS от root:
   ```bash
   DOMAIN=crm.example.ru EMAIL=admin@example.ru bash bootstrap-vps.sh
   ```
   Скрипт поднимает Node 24, PostgreSQL, Nginx, **получает сертификаты
   Let's Encrypt** для `DOMAIN` и `staging.DOMAIN` (переменная
   `STAGING_DOMAIN`), включает редирект на HTTPS и HSTS, создаёт
   пользователя `deploy`, обе БД, оба systemd-сервиса (с `TZ`, по умолчанию
   `Europe/Moscow`), ключ для чтения приватного репозитория (скрипт
   остановится и попросит добавить его в GitHub → Settings → Deploy keys)
   и ключ для доступа GitHub Actions к серверу. Без `DOMAIN` всё работает
   по HTTP на IP (80 и 8080) — только для первого взгляда.
2. Staging закрыт HTTP basic auth (логин `staging`, пароль печатается в
   конце и лежит в `/root/.staging-basic-auth`).
3. **Бэкапы**: `deploy/backup.sh` ставится в cron на 03:00, делает
   `pg_dump` обеих баз в `/opt/backups/revenue-saas`, хранит 14 дней
   (команда восстановления — в комментарии скрипта). **Самопроверка**:
   `deploy/healthcheck.sh` раз в 5 минут дёргает `/api/health` и
   перезапускает упавший сервис (лог `/var/log/revenue-healthcheck.log`).
4. В конце скрипт выведет значения для GitHub → `Settings → Secrets and
   variables → Actions`: обязательные `VPS_HOST`, `VPS_USER`,
   `VPS_SSH_KEY`; при HTTPS дополнительно `PROD_URL`
   (`https://crm.example.ru`), `STAGING_URL`
   (`https://staging.crm.example.ru`) и `STAGING_BASIC_AUTH`
   (`staging:пароль`) — их использует health-check в workflow.

После этого весь дальнейший процесс — просто `git push` в `staging` или
`main`: GitHub Actions сам зайдёт на сервер, подтянет код, соберёт,
прогонит миграции, перезапустит нужный сервис и проверит, что
`/api/health` отвечает (а не только статика Nginx).

Nginx отдаёт `index.html` с `Cache-Control: no-cache`, а хешированные
`/assets/` — с годовым кешем: после деплоя браузер никогда не держит
старый `index.html` со ссылками на удалённые бандлы.

Для 1 ГБ RAM в `/etc/postgresql/16/main/postgresql.conf` разумно
задать: `shared_buffers = 128MB`, `work_mem = 4MB`,
`maintenance_work_mem = 32MB` (входит в скрипт `bootstrap-vps.sh`).

### Продвижение изменений staging → production

Когда изменения проверены на staging, слить `staging` в `main` и
запушить — production обновится сам:

```bash
git checkout main && git merge staging && git push origin main
```

### Ручной запуск деплоя (без пуша)

Во вкладке репозитория **Actions** можно нажать "Run workflow" на
`Deploy to staging` или `Deploy to production` — это тот же процесс,
что и автоматический пуш (полезно, если нужно передеплоить без новых
коммитов, например после смены `.env` на сервере).
