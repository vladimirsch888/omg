# Техническая документация системы учёта выручки

Внутренний документ по устройству системы: стек, архитектура, модель
данных, бизнес-логика расчётов, API, инфраструктура и деплой.

---

## 1. Что это за система

Веб-приложение для учёта выручки и прибыли IT-компании, которая
продаёт лицензии (amoCRM, Wazzup, NOVA и т.п.), внедряет их и
сопровождает клиентов.

Система закрывает четыре задачи:

1. **Деньги** — доходы и расходы, PnL (прибыли/убытки) и ДДС (движение
   денежных средств), сколько денег реально свободно к использованию.
2. **Продажи** — разовые продажи, подписки на лицензии с продлением,
   план продаж на год и на каждый месяц.
3. **Клиенты и работа** — клиенты, дерево проектов и подпроектов,
   заявки клиентов, учёт часов сотрудников.
4. **Аналитика** — прибыль по клиентам (LTV), структура расходов,
   доля прибыли от лицензий и от работ, фактические сроки проектов.

Приложение мультиарендное на уровне схемы данных: у каждой сущности
есть `organizationId`, все запросы фильтруются по организации текущего
пользователя.

## 2. Стек

```
apps/api   Node.js 24 LTS + Hono + TypeScript 7 + Prisma 7 (Rust-free, pg adapter) + PostgreSQL 16
apps/web   React 19 + Vite 8 (Rolldown) + TypeScript 7 + Tailwind CSS v4 + Recharts 3
```

Монорепозиторий на npm workspaces, два пакета: `apps/api` и `apps/web`.

### Почему именно эти технологии

Ключевое ограничение — приложение должно быть лёгким и быстрым на
недорогом VPS (1 vCPU / 1 ГБ RAM). Поэтому вместо привычной связки
Express + Prisma с Rust-движком выбрано следующее:

| Технология | Причина выбора |
|---|---|
| **Hono** вместо Express | Кратно выше пропускная способность и заметно меньше памяти на соединение. При этом это обычный mainstream-фреймворк, работает на стандартном Node.js через `@hono/node-server`. |
| **Prisma 7 в Rust-free режиме** | С 7-й версии клиент не тянет отдельный Rust-бинарник query-engine (раньше — отдельный процесс на десятки МБ и медленный старт). Запросы идут напрямую через драйвер `pg` (`@prisma/adapter-pg`). Собранный API держит **~85–110 МБ RSS** на реальном Postgres 16. |
| **Node.js 24 LTS** | Актуальный LTS. Ставится на Ubuntu 24.04 через официальный репозиторий NodeSource (в штатных репозиториях Ubuntu версия устаревшая). |
| **TypeScript 7** (нативный компилятор на Go) | Тот же пакет `typescript` и та же команда `tsc`, но проверка типов и сборка в 8–12 раз быстрее. |
| **Vite 8 на Rolldown** (Rust-бандлер) | Сборка фронтенда ~1 секунда даже на слабом CPU — это важно, так как сборка идёт прямо на VPS при деплое. |
| **Tailwind CSS v4** | Новый Rust-движок (Oxide), меньше итоговый CSS, конфигурация прямо в CSS-файле, без `tailwind.config.js`. |
| **React 19 + React Router 7** | Фронтенд собирается в статические файлы и раздаётся Nginx — сам React не потребляет ресурсы сервера, только браузер клиента. |
| **Recharts 3** | Графики. Подключается лениво (см. раздел «Графики»), чтобы не утяжелять основной бандл. |

Итог: PostgreSQL + один Node-процесс спокойно работают на VPS
1 vCPU / 1 ГБ RAM.

## 4. Модель данных (`apps/api/prisma/schema.prisma`)

### Организация и пользователи

- **Organization** — компания. Валюта по умолчанию RUB.
- **User** — вход по email/паролю (`bcryptjs`), роли
  `OWNER / ADMIN / MANAGER / VIEWER`, флаг `isActive`.

### Клиенты и проекты

- **Client** — B2B-клиент: название, юрлицо, ИНН, контакты, статус
  (`ACTIVE / PAUSED / CHURNED`), заметки.
- **Project** — **трёхуровневая структура «клиент → проект →
  подпроект»**: у проекта есть `clientId` и необязательный `parentId`.
  Подпроект — тот же `Project` с заполненным `parentId`; глубина
  ограничена одним уровнем вложенности (у подпроекта не может быть
  своих подпроектов, константа `MAX_PROJECT_DEPTH = 2`).
  Деньги и часы подпроекта **не дублируются**, а агрегируются в отчётах
  родителя через рекурсивный обход дерева
  (`getProjectAndDescendantIds`).
  Статус `CLOSED` = «работы завершены»: кнопка «Проект завершён»
  проставляет его вместе с сегодняшней датой в `endDate`; возврат в
  работу очищает `endDate`.
  Дополнительно: `hourlyRate`, `budgetHours`, `startDate`, `endDate`,
  тип проекта из справочника.

### Справочники

- **DictionaryType / DictionaryValue** — универсальный справочник
  («разделы» и их значения), полностью наполняется из админки.
  Из коробки при регистрации организации создаются разделы:
  `operation_category` (категории операций: лицензии amoCRM/Wazzup/NOVA,
  работы по клиенту, сопровождение, зарплата, закупка лицензий у
  поставщика, хостинг и ПО, маркетинг и т.д.), `project_type`,
  `payment_method`, `request_type`.

### Товарная матрица и продажи

- **LicenseProduct** — продукт каталога с типом `ProductType`:
  - `LICENSE` — лицензия по подписке: `defaultDurationMonths` (срок
    цикла в месяцах), `defaultPrice`, `defaultVendorSharePercent`
    (доля вендора, по умолчанию 50), `defaultTaxable`;
  - `WORK` — разовые работы: вместо срока подписки — `defaultWorkDays`
    (оценка в рабочих днях; используется для автоподсчёта «Даты
    окончания работ» в продаже).
  Значения продукта — только **умолчания**: они копируются в подписку
  или продажу и дальше живут независимо от изменений каталога.
- **Subscription** — подписка клиента на лицензию. Хранит **снимок
  условий сделки** (`price`, `durationMonths`, `vendorSharePercent`,
  `taxable`), статус (`ACTIVE / PAUSED / CANCELLED`), `startDate`,
  `nextBillingDate` и `invoiceSentAt` (см. ниже).
- **Sale** — разовая продажа: сумма, `saleDate`, необязательная
  `workEndDate` (только для WORK-продуктов), снимок доли вендора и
  налогооблагаемости. **Всегда несёт `clientId` напрямую**, даже если
  проект не указан — иначе выручка была бы невидима для отчётов по
  клиенту.

### Деньги

- **Operation** — доходная или расходная операция:
  - `type`: `INCOME` / `EXPENSE`;
  - `status`: `PLANNED` / `ACTUAL`;
  - **`accrualDate`** — дата начисления, идёт в **PnL**;
  - **`paymentDate`** — дата оплаты, идёт в **ДДС**; `null` = деньги
    ещё не двигались;
  - категория и способ оплаты из справочников, контрагент, описание;
  - `vendorSharePercent` и `taxable` — параметры финансового водопада;
  - необязательные связи `subscriptionId` / `saleId` — операции,
    порождённые подпиской или продажей;
  - `projectId` необязателен: бывают общекорпоративные операции
    (зарплата, хостинг), не привязанные к проекту.

### Заявки и часы

- **Request** — заявка клиента, привязана к проекту: статус
  (`OPEN / IN_PROGRESS / DONE / CANCELLED`), приоритет
  (`LOW / MEDIUM / HIGH`), тип из справочника.
- **TimeEntry** — часы сотрудника по проекту и, опционально, по заявке.

### План продаж

- **SalesPlan** — цель по продажам. `month = null` означает **годовой**
  план, `1..12` — **месячный**. Годовой и месячные планы задаются
  независимо и не обязаны сходиться; интерфейс показывает расхождение.
  Уникальность `(organizationId, year, month)` обеспечивается в сервисе,
  **не** уникальным индексом: PostgreSQL считает NULL-значения
  различными, поэтому индекс допустил бы два годовых плана на один год.

### Флаг `isDemo`

У Client, Project, Operation, Request, TimeEntry, LicenseProduct,
Subscription, Sale и SalesPlan есть флаг `isDemo`. Удаление демо-данных
затрагивает **только** записи с `isDemo = true`.

## 5. Финансовая логика

### 5.1. Финансовый водопад (`modules/finance/waterfall.ts`)

Единая точка расчёта чистой прибыли во всей системе. Для одной
входящей суммы:

```
сумма от клиента (amount)
  − vendorCost    = amount × vendorSharePercent / 100   (доля вендора; 0 для собственных услуг)
  = taxBase                                             (то, что осталось после вендора)
  − taxReserve    = taxBase × TAX_RESERVE_PERCENT / 100 (резерв на налог; 0, если taxable = false)
  = spendable                                           (свободные деньги)
```

`TAX_RESERVE_PERCENT` задаётся переменной окружения, по умолчанию **7 %**
(упрощённая модель УСН «доходы»; точная поквартальная механика и пороги
намеренно вне области задачи).

**Важно:** везде, где в системе написано «чистая прибыль», имеется в
виду именно `spendable` — доход **минус доля вендора И минус налоговый
резерв**, а не только доля вендора.

`taxable = false` используется для необлагаемых поступлений (например,
прямой перевод на карту).

### 5.2. Подписки (`modules/subscriptions/subscriptions.service.ts`)

**Создание подписки** сразу выставляет первый платёж: создаётся
INCOME-операция и, если есть доля вендора, связанная EXPENSE-операция
(«Оплата вендору за лицензию»). Дальше на каждый период — одна кнопка
**«Продлить»** (`POST /api/subscriptions/:id/bill`), которая делает то
же самое.

При продлении можно **изменить сумму**: `bill` принимает необязательный
`amount`. Новая сумма проводится за этот период и **сохраняется как
`price` подписки**, то есть становится суммой по умолчанию для всех
следующих продлений.

**Стадия «Счёт отправлен».** `Subscription.invoiceSentAt` — дата, когда
клиенту выставили счёт за следующий период. Деньги ещё не пришли,
поэтому это не операция, а пометка: строка подсвечивается жёлтым и
получает бейдж «счёт от <дата>».
`POST /api/subscriptions/:id/invoice-sent` ставит отметку, `DELETE` того
же адреса снимает её. `billSubscription` очищает её сам: продление
закрывает тот период, ради которого счёт и выставляли. Хранится дата,
а не флаг, — чтобы было видно, сколько клиент «сидит» на счёте.

**Раздельные даты — важный момент.** Дата операции и дата следующего
платежа считаются по-разному:

- операция (INCOME/EXPENSE) датируется **моментом нажатия «Продлить»**
  (`new Date()`) — когда деньги реально пришли;
- `nextBillingDate` продвигается на `durationMonths` от **прежнего**
  `nextBillingDate`, а не от даты клика.

Это намеренно: если продлить просроченную подписку сегодня, платёж
должен попасть в текущий месяц как факт, а график следующих платежей не
должен «поехать» из-за опоздания. `durationMonths` — произвольное
число месяцев (1, 6, 7, 12, 13, 25…), не привязано к календарному году.

**Сводка за месяц** (`getMonthSummary`, `GET /api/subscriptions/month-summary`):

| Показатель | Как считается |
|---|---|
| `renewedAmount` | Сумма INCOME-операций от подписок с `accrualDate` в текущем месяце |
| `renewedNetProfit` | То же, но через `computeWaterfall(...).spendable` |
| `pendingNetProfit` | **Только прогноз**: активные подписки с `nextBillingDate` до конца месяца (включая просроченные), без факта |
| `totalExpected` | `renewedAmount` + сумма ожидаемых |
| `invoicedAmount` / `invoicedCount` | Активные подписки с непустым `invoiceSentAt`. Это **подмножество** ожидаемого, а не добавка: та же подписка продолжает учитываться в прогнозе, пока «Продлить» не проведёт платёж. Не ограничено текущим месяцем — счёт из августа, до сих пор не оплаченный, это деньги, которых ждут сегодня |

### 5.3. План продаж (`modules/salesPlans/salesPlans.service.ts`)

**Факт** — начисленный доход (та же база, что и PnL): цель измеряется
против выручки, которую месяц заработал, а не против того, когда деньги
физически пришли.

**Прогноз с учётом подписок** (`addSubscriptionForecast`) — обходит
график платежей каждой активной подписки до конца года и раскладывает
каждый ещё не проведённый период по месяцам. Два правила:

- прогнозируется **только текущий месяц и дальше** — прошлые месяцы
  показывают факт, и подмешивание прогноза туда сделало бы историю
  план/факт неправдой;
- просроченная подписка (`nextBillingDate` уже прошёл) прогнозируется
  в текущий месяц — эти деньги ждут сейчас.

**Разделение прибыли на лицензии и работы** (`classifyIncome`) — по
убыванию достоверности:

1. операция от подписки → всегда лицензия;
2. операция от продажи → тип продукта (`LICENSE` / `WORK`) решает;
3. ручная операция, категория которой каталог однозначно относит к
   одному типу (`getCategoryKinds`: категория, которую используют
   только LICENSE-продукты, — лицензионная; только WORK-продукты —
   рабочая; используемая обоими — неоднозначна и намеренно не
   размечается);
4. ручная операция с ненулевой долей вендора → лицензия (в этом бизнесе
   долю платят только за перепродаваемую лицензию).

Всё остальное остаётся в категории `other`, а не запихивается в один из
двух ящиков, — чтобы проценты описывали реальные деньги, а не догадку.

Правила выводятся **из собственного каталога организации**, а не из
захардкоженных кодов справочника: коды редактируются пользователем, и
компания, добавившая свои категории и продукты, получит правильный
ответ без правки кода.

### 5.4. Фактический срок проекта (`modules/projects/projects.service.ts`)

`buildProjectTimeline` возвращает:

- **`startedAt`** — `startDate` проекта, если заполнен, иначе самое
  раннее реальное событие: операция (`accrualDate`), заявка
  (`createdAt`) или списанные часы (`date`). Поле `startSource`
  (`planned` / `activity`) говорит, откуда взята дата.
- **`finishedAt`** — `endDate` завершённого проекта; если проект закрыт
  без даты — последняя активность. Пока проект в работе — `null`, и
  срок считается по сегодняшний день.
- **`calendarDays`** — календарные дни, включая обе граничные даты
  (1 сентября → 1 сентября = 1 день).
- **`workingDays`** — то же без суббот и воскресений (производственный
  календарь не учитывается). Это та же единица, в которой оценивается
  WORK-продукт (`defaultWorkDays`), поэтому план и факт сравнимы.

Даты собираются по проекту **и всем его подпроектам** — тем же
`getProjectAndDescendantIds`, что используется для денег и часов.

### 5.5. Целостность связей клиент / проект / продукт / продажа

Проект не обязателен ни у операции, ни у подписки, ни у продажи —
общекорпоративные расходы и прямые продажи без проекта существуют
легально. Из этого следует, что все места, считающие деньги по
клиенту, обязаны учитывать **три пути привязки** (проект → клиент,
подписка → клиент, продажа → клиент), а не только через проект:

- **LTV клиента** — суммирует операции по проектам клиента **плюс**
  операции, связанные с его подписками и продажами;
- **фильтр по клиенту в PnL/ДДС** — строится по тем же трём путям.

При создании подписки и продажи проверяется, что выбранный проект
принадлежит указанному клиенту (аналогично проверке родитель/подпроект
при создании проекта) — иначе выручка клиента могла бы «утечь» на чужой
проект.

## 6. API

Базовый префикс — `/api`. Аутентификация — JWT в заголовке
`Authorization: Bearer <token>`. Ответы и ошибки — JSON;
ошибки валидации Zod и `AppError` приводятся к `{ "error": "текст" }`.
`GET /health` — проверка живости (без авторизации).

### Аутентификация и пользователи

## 7. Frontend

### Маршрутизация и состояние

React Router 7, защищённые маршруты через `ProtectedRoute`.
`AuthContext` хранит токен в `localStorage` и подставляет его в
axios-инстанс (`api/client.ts`); 401 приводит к разлогину.
Локального стора нет — данные грузятся страницами по мере надобности.

### Дизайн-система

Две темы на одном наборе имён. Палитра задаётся через `@theme` в
`src/index.css`:

- поверхности: `canvas` → `surface` → `raised` → `overlay`;
- линии: `line`, `line-strong`;
- текст: `ink` / `ink-muted` / `ink-subtle`;
- акцент — приглушённый петроль;
- три финансовых цвета: `income` (сдержанный изумруд), `expense`
  (терракота), `reserve` (охра).

**Тёмная тема** (тёплый графит, не чёрный) — значение по умолчанию.
**Светлая** (тёплый белый) переопределяет **те же переменные** в блоке
`:root[data-theme="light"]`, поэтому ни один `bg-surface` или
`text-ink` в коде не знает о существовании тем.

Ярких «светофорных» красного и зелёного нет намеренно — именно они
делают финансовый интерфейс дешёвым и тревожным. Шрифт — Inter
(self-hosted, без внешнего CDN). Все денежные суммы идут табличными
цифрами (`.tnum`), чтобы колонки не «прыгали».

Тему выбирает пользователь в **Настройки → Оформление**: «Как в
системе» (следует `prefers-color-scheme`), «Светлая», «Тёмная». Выбор
хранится в `localStorage`, применяется `ThemeContext`, а инлайновый
скрипт в `index.html` проставляет `data-theme` **до первой отрисовки** —
иначе страница мигнёт тёмной темой перед монтированием React.

### UI-кит (`src/components/ui`)

`Button` / `IconButton`, `Field` + `Input` / `Select` / `SelectCompact` /
`Checkbox` / `ReadonlyValue`, `Badge` / `StatusBadge`, `Card` /
`ListCard` / `StatCard` / `PageHeader`, `DataTable` + `RowCard` +
`MetaItem`, `Modal`, `Skeleton` / `PageSkeleton` / `EmptyState` /
`InlineBar`, `Sparkline` / `Delta`.

Два принципиальных решения:

- **`DataTable` рендерит одни и те же данные двумя способами**: таблицей
  от брейкпоинта `sm` и выше, а на телефоне — карточками (`RowCard`).
  Горизонтального скролла таблиц в приложении нет вообще.
- **`UiProvider` заменяет `window.confirm` / `prompt` / `alert`** на
  собственные модалки и тосты: `const ui = useUi()` →
  `await ui.confirm(...)`, `await ui.prompt(...)`, `ui.toast(...)`.
  Системные диалоги браузера на iOS показывают домен сайта над текстом
  и не поддаются стилизации.

### Графики (`src/components/charts`)

Recharts — самая тяжёлая зависимость фронтенда, поэтому **каждый график
подключается через `React.lazy` и обёртку `LazyChart`**: страница со
списком не тянет библиотеку вообще (основной бандл ~410 кБ вместо
~760 кБ).

Общий вид задан в `charts/theme.ts` — тонкие линии, только
горизонтальная сетка, свои тултипы (`ChartTooltip`), сокращённые
подписи осей (`450 тыс`, `1,2 млн`, через неразрывный пробел, чтобы
подпись не переносилась). Recharts принимает цвета строками и не умеет
читать CSS-переменные, поэтому обе палитры лежат в том же файле, а хук
`useChartColors()` отдаёт нужную и перерисовывает графики при смене
темы.

Графики: `TrendChart` (прибыль и денежный поток), `PnlBars`,
`CashFlowChart`, `CategoryDonut` (структура расходов), `PlanFactChart`
(план/факт со стопкой «Факт + Прогноз»), `ProfitMixDonut` (лицензии и
работы). Спарклайны в KPI-карточках нарисованы вручную на SVG
(`ui/Sparkline.tsx`) — ради них не имеет смысла грузить recharts на
первый экран.

### Мобильная адаптация

- Сайдбар превращается в выезжающую панель на экранах уже `lg`
  (≤1024px); на телефоне — нижний таб-бар (Дашборд, Подписки, Продажи,
  Клиенты, «Ещё») и липкая шапка с названием раздела.
- Все поля ввода — минимум 16px, иначе Safari на iOS автоматически
  зумит страницу при фокусе.
- Единицы высоты `dvh` вместо `vh`, чтобы вёрстка не прыгала при
  скрытии панели адресной строки.
- Учтены `env(safe-area-inset-*)` под чёлку и индикатор жеста.
- Тап-таргеты не меньше 44px.
- Проверено эмуляцией iPhone (headless Chromium): горизонтального
  скролла страниц нет ни в одном разделе.

## 8. Демо-данные (`modules/demo/demo.service.ts`)

Вся логика в одном файле: `seedDemoData` / `clearDemoData` /
`getDemoStatus`. Локальный `prisma/seed.ts` вызывает тот же
`seedDemoData`, поэтому определение демо-набора не дублируется.

`POST /api/demo/seed` создаёт для текущей организации:

- 4 клиента;
- **7 проектов**, включая подпроекты (чтобы показать роллап) и один уже
  завершённый с заполненными датами начала и окончания (чтобы сразу
  было видно серое отображение и отчёт по сроку реализации);
- 6 продуктов (4 лицензии + 2 разовые работы);
- 4 подписки с историей платежей, одна из них — с отметкой «Счёт
  отправлен»;
- 5 разовых продаж, включая продажи без привязки к проекту (проверка,
  что LTV и отчёты по клиенту не теряют такую выручку) и продажу
  WORK-продукта с заполненной «Датой окончания работ»;
- операции за последние ~8 месяцев по всем категориям, включая один
  запланированный, но неоплаченный доход — чтобы PnL и ДДС различались;
- заявки и записи учёта часов;
- планы продаж на текущий год: годовой и двенадцать месячных,
  намеренно не ровно по одной двенадцатой, чтобы на графике план/факт
  были и перевыполненные, и проваленные месяцы.

**Политика поддержки:** при добавлении новой функции (новая модель,
новая категория справочника, новое измерение в отчётах) — расширять
`demo.service.ts`. Цель: после нажатия «Наполнить демо-данными» ни один
раздел или отчёт не остаётся пустым.

## 11. Инфраструктура и деплой

Обе среды живут на одном VPS (Ubuntu 24.04), каждая — со своей БД,
своим `.env`, своим systemd-сервисом и своим портом:

| Среда | Ветка | Директория | Порт API | Адрес |
|---|---|---|---|---|
| staging | `staging` | `/opt/revenue-saas-staging` | 4001 | `http://IP:8080/` |
| production | `main` | `/opt/revenue-saas-prod` | 4000 | `http://IP/` |

**Деплой полностью автоматический** через GitHub Actions
(`.github/workflows/deploy-staging.yml`,
`deploy-production.yml`): пуш в `staging` разворачивает staging, пуш в
`main` — production. Workflow заходит на сервер по SSH и выполняет:

```
git fetch && git reset --hard origin/<branch>
npm install
npm run build:api
npm run prisma:deploy --workspace apps/api   # применение миграций
npm run build:web
systemctl restart revenue-api-<env>
```

затем делает health-check HTTP-запросом.

**Единоразовая настройка сервера** — скрипт `deploy/bootstrap-vps.sh`
на чистом VPS от root: ставит Node 24, PostgreSQL, Nginx, создаёт
пользователя `deploy`, обе БД, оба systemd-сервиса, оба конфига Nginx,
deploy-ключ для чтения репозитория и ключ для доступа GitHub Actions.
В конце выводит три значения для GitHub → *Settings → Secrets and
variables → Actions*: `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`.

Для 1 ГБ RAM в `postgresql.conf` задаются `shared_buffers = 128MB`,
`work_mem = 4MB`, `maintenance_work_mem = 32MB` (входит в скрипт).

**Продвижение staging → production:**

```bash
git checkout main && git merge staging && git push origin main
```

Во вкладке **Actions** можно запустить деплой вручную («Run workflow»)
без новых коммитов — например, после смены `.env` на сервере.

### Рабочий процесс разработки

1. Все изменения сначала уходят в ветку `staging` и проверяются на
   тестовом сервере.
2. В `main` (production) изменения попадают только явным слиянием после
   проверки.
3. Миграции — только аддитивные при продвижении в прод; перед слиянием
   проверяется, что в накопленных миграциях нет `DROP` / `DELETE` /
   `TRUNCATE`.

## 12. Ограничения и возможные следующие шаги

Известные упрощения:

- налоговый резерв — плоский процент, без поквартальной механики и
  порогов УСН;
- производственный календарь не учитывается: «рабочие дни» — это все
  дни, кроме субботы и воскресенья;
- мультиарендность заложена в схеме, но интерфейса управления
  организациями нет — одна организация на инсталляцию;
- валюта одна (RUB), поле `currency` зарезервировано;
- роль `VIEWER` не ограничена на запись в обычных разделах: `requireRole`
  стоит только на администрировании (пользователи, справочники, каталог,
  демо-данные), режима «только чтение» пока нет.

Направления развития:

- импорт платежей из банковских выписок и API amoCRM / Wazzup / NOVA;
- бюджетирование по расходам и план-факт по затратам;
- экспорт отчётов в Excel / PDF;
- уведомления о приближающихся продлениях и просроченных счетах.
